# Abyssal Security Model

No application has absolute security. Abyssal implements OPAQUE authentication, pairwise Olm Double Ratchet encryption for direct chats, and RFC 9420 MLS for rooms, but it has not received an independent audit and must not be presented as Signal-equivalent.

## Current Protections

- Relay state is process memory only: keyed invite-code identifiers, OPAQUE password files, encrypted identity envelopes, sessions, room catalog, presence, recipient-specific pending ciphertext, and attachments have no database or volume. Plaintext invite codes exist only until their one-time startup print, then those buffers are zeroized.
- Android app-owned account, message, endpoint, PIN, password, token, and key state is process memory only. `FLAG_SECURE`, hidden-overlay rejection on Android 12+, and recents-screenshot disabling on Android 13+ reduce normal screen-capture and overlay exposure. Calculator camouflage keeps only salted PBKDF2-HMAC-SHA256 verifiers in RAM, compares derived values without early exit, serializes attempts, and applies bounded exponential backoff. Process death resets the launcher alias and verifier, there is no default PIN, and the user must configure camouflage again after a fresh process.
- Web client uses no persistent browser storage, cookies, service worker, source maps, or third-party runtime scripts. Identity keys live in the shared Rust/WASM core; typed password, plaintext, and key buffers are overwritten on a best-effort basis after use.
- Every protocol-v9 and protocol-v10 text or attachment-metadata plaintext carries a sender-client origin tag (`android` or `web`) asserted by the sending build. It travels only inside the authenticated encrypted payload, so the relay cannot observe, strip, or forge it. Receivers show a per-message origin badge and fail closed on missing or unknown tags.
- OPAQUE registration and login use the shared Rust `opaque-ke` implementation. Password bytes never appear in relay application requests. Registration additionally requires an Ed25519 proof of possession over the protocol-v9 transcript, the node identifier, handshake identifier, fresh server challenge, exact registration upload, identity public key, prekey pool, fallback key, and encrypted identity envelope. The proof is verified before the one-time invite code is consumed or the account is created. Identity and ratchet snapshots are encrypted with an OPAQUE export-key-derived key before leaving the client.
- Protocol-v9 text, read-receipt, and control metadata use a fresh content key and ChaCha20-Poly1305 with conversation/message/sender additional data. Each recipient's content key is wrapped through an authenticated `vodozemac` Olm Double Ratchet session configured for a full-length HMAC. Every recipient envelope contains exactly one 64-byte Ed25519 signature over the v9 version, authenticated context, common nonce/ciphertext, sender identity key, intended username, prekey metadata, and recipient-specific ratchet envelope. Each successful encrypt/decrypt result also carries an Ed25519 signature over the complete encrypted identity state, public identity bundle, prekey ID, and bounded monotonic revision. Before leasing prekeys, registering replay IDs, or applying an identity revision, the relay verifies the envelope and state signatures with the authenticated account's long-term Ed25519 identity and the shared Rust-core transcript builders. The public identity bundle is exactly 608 bytes: a stable 64-byte identity portion, 16 canonical 32-byte one-time keys covered by the signed identity bundle, and one 32-byte fallback key. Initial asynchronous messages use a recipient-specific leased one-time prekey. Prekey IDs are deterministic commitments to their public keys; recipients verify relay metadata against the one-time key inside the Olm envelope before changing ratchet state. The authenticated lease is issued before first-contact encryption and binds sender, chat, recipient, message, and prekey; it has a 30-second idle TTL, with global capacity 4,096 and per-recipient capacity 16. A matching accepted pending frame pins its lease beyond the idle TTL until acknowledgement, eviction, queue removal, or the bounded pending-message TTL. An exact ACK transaction removes the consumed lease, applies the one-for-one prekey replacement, and preserves other live leases; malformed, duplicate, or mismatched ACKs do none of these. Clients bind lease work to the active connection generation and release a lease only when it is definitely unused. The default pending TTL is 24 hours, configurable through `ABYSSAL_PENDING_MESSAGE_TTL_HOURS` and clamped to 1-168 hours; zero is never treated as unbounded. The ACK has a separate action-only signature over conversation, message, original sender, and consumed prekey; the signed recipient state update and pending-frame removal precede `ack_result`. The relay receives ciphertext, signatures, public identity bundles, prekey metadata, ratchet envelopes, and OPAQUE-encrypted state snapshots, not plaintext or ratchet secrets. Protocol-v8 shapes and state are rejected fail closed.
- Every protocol-v9 encrypted payload is authenticated after padding its plaintext into a mandatory 256-byte length bucket. The padding header authenticates the original length and random filler; this reduces plaintext-length leakage only to bucket boundaries. It is not full traffic padding: packet timing, frame counts, routing, and the selected bucket remain observable.
- Protocol-v10 rooms use `mls-rs 0.55.4` with the RustCrypto provider `0.22.1`. Each room has an independent random group identifier, MLS epoch, membership transcript, and roster. Owner-approved key-package joins produce MLS Welcome messages; owner-approved additions and removals advance the group epoch. Room text, attachment metadata, and read receipts are encrypted as MLS application messages rather than pairwise fanout. The relay validates authenticated room authority, exact epoch/digest/roster transitions, replay IDs, queue bounds, and per-member state ownership, but receives only opaque MLS control/application ciphertext and OPAQUE-export-key-sealed client snapshots. Attachment bulk bytes remain separately encrypted cipher-v1 XChaCha20-Poly1305 blobs, and their keys travel only inside MLS application metadata.
- MLS state changes are transactional. A sender stages its next group state and commits it only after an exact accepted `mls_room_result`; rejection or a definitely not-sent result rolls back, while an ambiguous result invalidates the local room state. A recipient stages native application/control processing and publishes or installs it only after an exact accepted `mls_snapshot_result`; rejection rolls back the native checkpoint. Relay snapshots, recovery snapshots, pending Welcome/control/application records, and replay windows are bounded and RAM-only. Reconnecting clients recover a historical snapshot and queued frames, remain `synchronized=false`, and cannot send until exact acknowledgements and a fresh current catalog re-establish synchronization.
- Direct protocol-v9 application message frames carrying text, read receipts, or attachment metadata use a mandatory canonical outer transport envelope in both directions: sender to relay and relay to recipient. The smallest valid UTF-8 application-frame buckets are `4096`, `16384`, `65536`, `262144`, and `1048576` bytes, with random URL-safe ASCII filler in `padding_bucket` and `padding`. The relay, web client, and Android client reject missing, malformed, noncanonical, truncated, or oversized envelopes before routing or domain-state installation, and clients strip the transport fields before retaining a frame. Rate, transient-fanout, pending, and outbound-queue budgets count the complete padded frame. This applies only to direct encrypted message frames, not WebSocket control frames or HTTP attachment bodies; JSON property order is not a security contract. The outer envelope reduces exact encrypted-message application-frame length leakage to bucket boundaries, but does not hide timing, counts, routing, participants, attachment sizes, relay or Cloudflare visibility, control-frame sizes, or bucket selection. It is wire-incompatible with older clients that omit padding even though the cryptographic payload remains protocol v9.
- Outbound ratchet state is staged until the relay returns an exact accepted `message_result` for the message ID. The relay preflights all recipient fanout and atomically admits the complete pending set before reporting acceptance; on admission failure it rolls back pending mutations. After an exact rejected or not-sent result, the client releases only leases definitely known to be unused. A dedicated result sink confirms that the result reached the sender's writer; sink failure invalidates the session. Clients commit the staged ratchet only after accepted fanout; a timeout, socket failure, or lost result is ambiguous, so the client closes the session and purges local state rather than guessing lease ownership or reusing the ratchet.
- A recipient publishes decrypted message, control, or read-receipt state only after an exact accepted `ack_result` for the same message ID. The relay accepts an ACK only after finding exactly one matching pending recipient frame and, for a leased first-contact frame, its matching lease; it then applies the signed recipient state mutation and removes that frame before emitting `ack_result`. Rejected, not-sent, timeout, disconnect, malformed, unknown, or duplicate ACK outcomes fail closed; pending ACKs are separately bounded at 64 on Android and 256 on web. This is delivery/state durability, not proof of human reading.
- Decryption is transactional around ratchet state. If Olm processing advances a session but outer AEAD/content-binding authentication, prekey rotation, revision update, or state sealing fails, the client restores the account, peer sessions, session-prekey map, advertised prekey metadata, and revision from a vodozemac pickle checkpoint before returning an error. A failed initial delivery therefore does not consume or rotate the leased prekey.
- Post-native-decrypt wrapper, schema, or state-install failures clear local identity/cipher state and fail closed; authentication failures before native return remain ordinary drops.
- Successful encryption and decryption advance a monotonic ratchet-state revision. The relay keeps only the latest encrypted snapshot in RAM, uses a 128-revision replay window to accept bounded network reordering without accepting a message revision twice, and never replaces newer state with an older snapshot. Recipient ciphertext remains queued until the relay emits `ack_result` after the signed recipient state update and pending-frame removal.
- The relay authoritatively binds delivered sender usernames/public keys to authenticated accounts and rejects missing, duplicate, or unauthorized recipient envelope sets. Clients reject malformed, tampered, wrongly addressed, or misbound payloads before parsing plaintext. State advances are limited to a 1,024-revision jump and a 128-revision reorder window; stale or duplicate snapshots cannot roll the relay backward.
- Direct conversations display a symmetric safety number derived from both identity public keys. An exact user confirmation after a separate-channel comparison is required for direct actions; participants can detect active relay key substitution only when they perform that comparison honestly.
- TLS/WSS is required for remote web nodes loaded from HTTPS. Loopback HTTP remains available for development.
- WebSockets require `abyssal-v1` plus a random `ticket.*` subprotocol issued by authenticated `POST /v1/ws-ticket`. Tickets are 32 random bytes, expire after 30 seconds, are stored only as digests, and are single-use; bearer tokens are rejected in WebSocket subprotocols. Browser WebSocket origins must match the node host or an exact `ABYSSAL_WEB_ORIGINS` entry.
- Relay responses set a restrictive CSP, no-store caching, frame denial, no-referrer, MIME sniffing denial, HSTS, permissions restrictions, and cross-origin headers.
- Browser account responses are read through a strict 768 KiB streaming cap with fatal UTF-8 decoding and bounded canonical fields. Browser, Android, and relay cap legacy/non-MLS text frames at 1 MiB before JSON parsing. Only strict protocol-v10 MLS frame families may use the separate 16 MiB cap needed for bounded Welcome, control, snapshot, and recovery records; a non-MLS frame cannot obtain that allowance merely by adding an MLS-looking field. Oversized or malformed frames fail the authenticated socket closed. Web `pagehide` synchronously revokes decrypted Blob URLs, clears session/message/navigation references and React state, destroys PIN verifiers, and hides the document before a possible back/forward-cache snapshot. Android picker callbacks are generation-scoped and stale results are ignored; both clients cap identity pins, replay IDs, own-message indexes, room catalogs, and presence/direct catalogs, rejecting malformed or case-colliding catalogs instead of partially applying them. With Remember Session, Android pause/stop retains the RAM session; camouflage may lock or hide UI and clear preview while in-flight session work remains generation-scoped. Unchecked lifecycle exit, logout, expiry, wipe, and process/page teardown invalidate or cancel applicable work. Android outbound text and read-receipt operations share a bound of 64, carry captured app generation and identity, and are cancelled on logout, expiry, or wipe. Room/direct catalog events use a bounded, drainable 1,152-event channel tagged with connection generation; disconnect drains it and stale-session events are rejected. Android repository mutations use a monotonic in-memory epoch and reject stale epochs after synchronous purge.
- Abnormal Android socket invalidation clears socket-scoped joins, catalogs, and identity authorization before reconnect.
- Android inbound ciphertext and room/direct catalog queues are bounded and connection-generation tagged. Queue overflow closes the socket and requires reconnect/resync; invalidation drains queued events, wipes ciphertext buffers, and rejects stale callbacks. Commands, sends, and ACKs are connection-generation-bound and cannot reach a replacement socket. A carried global-wipe signal survives same-account reconnect, while explicit logout drains pending wipe and queued work.
- Android and web cap decrypted history at 500 messages or an estimated 8 MiB per chat, and 5,000 messages or an estimated 32 MiB globally, whichever limit is reached first. Deterministic timestamp, conversation, and message-ID tie-breaking keeps oldest-first eviction consistent across out-of-order delivery. Expiry, eviction, and memory clearing wipe mutable attachment-key arrays and best-effort release plaintext references. These conservative estimates bound application-owned history; immutable JVM/JavaScript strings, garbage collectors, browser engines, and the OS may retain copies, so this is not a physical-zeroization guarantee.
- Login and registration request bodies are capped at 16 KiB, OPAQUE handshakes expire after 60 seconds and are capped at 1,024 live entries, and known account-code starts are limited to six per minute. Unknown HMAC-derived code IDs are rejected before they can allocate limiter state, so random-code floods cannot fill the bounded map and deny real invite holders. WebSocket frame size/rate, outbound frame size, pending queue depth (500 frames per recipient and 256 MiB globally), pending-message lifetime (default 24 hours, clamped to 1-168 hours), session inactivity, global room catalog size (1,024), and per-user room count are bounded. Live outbound WebSocket queues additionally cap queued bytes at 4 MiB per client and 64 MiB globally; the relay rejects or closes slow consumers before unbounded frame cloning. Dead-man activity is updated only after successful authenticated operations, not invalid account handshakes. Wipe/control frames use a dedicated priority channel; the writer handles them before normal data and drops queued sensitive data when the connection terminates.
- Attachment plaintext limits are 20 MiB for images, 100 MiB for videos, and 200 MiB for other files. Bulk data uses a stateless binary XChaCha20-Poly1305 blob: one version byte, a 24-byte nonce, ciphertext, and a 16-byte tag, for exactly 41 bytes of wire overhead. The attachment key is delivered inside encrypted direct-chat v9 metadata or room v10 MLS application metadata; the relay never receives it. A weighted encrypted-attachment RAM pool is bounded globally and per account (default per-account quota: 320 MiB); the global pool includes stored blobs and in-flight upload/download references. An independent record quota counts the authoritative bounded attachment map: `ABYSSAL_ATTACHMENT_RECORD_LIMIT` defaults to 16,384 globally and `ABYSSAL_ATTACHMENT_ACCOUNT_RECORD_LIMIT` defaults to 4,096 per account; both clamp to 1-65,536, with the account limit capped by the global limit. Uploads reject a saturated record count before reading the request body, then recheck it atomically at final admission; record or byte exhaustion returns only generic HTTP 507 capacity. Expiry, deletion, completion cleanup, room cleanup, and global wipe remove records and naturally free record capacity. These record limits do not change the byte quotas. Every blob also has a finite relay-side expiry: `ABYSSAL_ATTACHMENT_MAX_LIFETIME_HOURS` defaults to 168 hours and is clamped to 1-720 hours, so an explicit `ttl=0` cannot leave an orphan immortal in RAM. Room absolute-expiry policy can shorten this hard cap. Upload request-body reads are capped at two concurrent bodies by default (maximum four), with a 30-second idle and 10-minute total deadline. Upload admission also requires the same generated message ID that is bound into the encrypted metadata. The relay stores that encrypted blob in a staged record that is non-downloadable to every user; staged records count against the existing byte and record quotas, have a 10-minute deadline clamped to final retention, and are swept every 30 seconds. After replay/state acceptance, the exact authenticated owner/chat/message transaction promotes the matching staged record server-side before fanout and result emission. Rejected, rolled-back, or never-sent messages do not publish the record; an accepted message whose result is lost still publishes it, and a duplicate live owner/chat/message binding is rejected without replacing ciphertext. The upload API now requires `message_id`; cipher-v1 bytes remain unchanged, direct metadata remains protocol v9, and room metadata uses protocol v10 MLS. Downloads use a separate bounded concurrency semaphore (default: 2; maximum: 16) and a capacity-one producer that releases its zeroizing buffer and permit after 30 seconds of backpressure, so large or stalled transfers cannot retain unbounded extraction resources.
- Every Android attachment upload, download, delete, completion, and claim release uses its captured `NodeSession`. Accepted publication is also guarded by the captured account, connection generation, and repository epoch; stale writes are rejected and attachment key material is wiped.
- Destructive attachment retention is explicit and recipient-scoped. A DM snapshots its intended peer and a room snapshots eligible members other than the uploader at upload time. The owner can preview without consuming a claim; each eligible recipient can have one active claim, and transport EOF alone never consumes it. If `Content-Length` is present, it must equal the exact metadata-derived ciphertext length. If it is absent, the client accepts only a bounded body that ends at that exact length; truncated, oversized, or otherwise malformed streams fail closed. The client authenticates and decrypts the ciphertext, then explicitly completes the recipient-bound claim before exposing plaintext. Failed, truncated, interrupted, cancelled, or unauthenticated transfers release the claim exactly once, including late responses; transfer buffers and attachment secrets are wiped. Concurrent claims by the same recipient are rejected; and the relay removes the encrypted blob and releases its quota only after every eligible recipient completes or the retention policy expires it. A one-time UI cannot prevent a malicious recipient from recording or copying content after decryption.
- Account-entry attempts are rate-limited per code, and a code cannot create a concurrent bearer session while its existing session remains unexpired.
- Relay and clients maintain bounded RAM replay windows keyed by conversation, authenticated sender, and message ID. Ratchet message keys are consumed after use, so cryptographic replays also fail. Duplicate ciphertext and receipt frames are rejected without growing unbounded state; each authenticated sender has a bounded live-entry quota, and saturated sender/global windows reject new IDs rather than evicting live entries and weakening the replay guarantee.
- Clients pin each observed account identity key for the current RAM session and terminate/drop state if that key changes. First-contact authenticity still requires out-of-band safety-number comparison.
- Sender usernames on delivered frames come from the authenticated relay session, not user-controlled encrypted metadata.
- Client and relay identity ingress reject malformed, zero, non-contributory, and known low-order X25519 public keys. One-time prekey identifiers are verified as commitments to the exact advertised public key before ratchet state changes.
- Room ownership and media-retention policy are enforced by the relay. Canonical DMs are visible only to their participants, and guessed chat IDs cannot be used to join a DM or transfer its attachments.
- By explicit product requirement, any authenticated account can request the global RAM wipe. This is an intentional availability tradeoff: compromise of one live account can destroy every account, room, pending frame, attachment, and invite-code set, forcing a visible destructive restart. The client keeps a confirmation step, but this is not an authorization boundary. The Android duress operation is account-stamped, so a stale evaluation cannot wipe a replacement login; a carried wipe survives same-account reconnect, while explicit logout drains pending wipe and queued work.
- Android and web attachment saves are explicit user actions. Clients authenticate and decrypt attachment ciphertext in memory, write the original bytes under a sanitized original filename, and best-effort wipe temporary byte arrays. One-time attachments have no save control. Saved files are plaintext by explicit user choice and inherit the destination provider's security. Android `2.0.0` and later also delete the obsolete device-bound export key created by older releases; this migration cleanup is not a new persistence path.

The 2026-08-22 integrated local gate ran 317 web tests, 53 Rust-core tests, 210 relay tests, and 222 Android tests. Web lint/build, Rust formatting and warning-denied Clippy, Android release lint and debug/release compilation, disposable-relay OPAQUE/direct-v9/room-v10 integration, deterministic generated-artifact and deployment checks, and npm/RustSec audits passed. No Android packaging task was invoked; the applicable tests had zero skips, failures, or errors. CodeQL remains a required remote post-push gate and is not represented as a local result.

## Residual Security Limits and Trust Assumptions

### Direct prekeys, MLS rooms, and multi-device limits

The previously identified initial prekey-pool exhaustion and lease-race issue is resolved in the current protocol-v9 implementation and covered by the integrated tests. Protocol v9 uses pairwise Olm Double Ratchet sessions. Deleted message keys provide the ratchet's forward-secrecy property, and reciprocal DH-ratchet steps provide recovery within an established session after key turnover. Per-recipient Ed25519 signatures authenticate the v9 envelope binding, and signed ratchet-state snapshots bind encrypted state, identity bundle, prekey pool, fallback key, and bounded revision. ACK action signatures are independent of state revision, but the relay applies the signed state and removes the pending frame atomically. Outbound state is staged and committed only after strict relay acceptance of complete recipient fanout; ambiguous delivery closes the session and is not retried with the same ratchet state. Attachment keys are delivered as ratcheted metadata and bulk bytes use a separate stateless XChaCha20-Poly1305 blob. Initial asynchronous sessions request an authenticated recipient-bound lease before first-contact encryption. The 608-byte public bundle contains a stable 64-byte identity portion, 16 canonical 32-byte one-time keys covered by the signed identity bundle, and a 32-byte fallback key. Leases bind sender, chat, recipient, message, and prekey; they expire after 30 seconds idle, with global capacity 4,096 and recipient capacity 16. Accepted pending frames pin their leases until acknowledgement, eviction, queue removal, or bounded pending-message expiry. An exact ACK removes only the consumed lease, applies one replacement prekey, and preserves other live leases. Clients bind lease operations to the connection generation and release only definitely unused leases. The default pending TTL is 24 hours and accepts only 1-168 hours, so a delayed ciphertext cannot race another sender for the same leased prekey or hold it indefinitely. This bounded queue lifetime remains an availability tradeoff while a frame is queued. Protocol-v8 shapes and state fail closed.

Rooms now use protocol-v10 RFC 9420 MLS rather than pairwise fanout. Membership changes advance the MLS epoch and update an exact authenticated roster. Each client owns a bounded sealed state snapshot; the relay remains the room-authority and delivery service without receiving the group secrets. A per-room replay window retains 2,048 application and membership IDs in both the native core and relay. The relay bounds the global room catalog at 1,024 entries, room membership at 117 accounts, per-member room count at 128, pending application count at 2,048, and queued room deliveries at 4,096. The underlying MLS secret-tree back-history is 1,024 generations. If expiry creates a sender-generation gap beyond that limit, the relay drops the undecryptable queued tail and marks the member unsynchronized until a membership epoch transition supplies recoverable current state. This is a bounded availability loss, not silent plaintext recovery.

The MLS implementation does not add multi-device coordination, a device list, or device-specific membership. One account is one active relay session. `mls-rs` has not received an independent Abyssal security audit, and its selected RustCrypto provider is explicitly marked experimental upstream. These remain release-blocking disclosures for any high-assurance claim.

### Directory verification limits

Presence carries the V2 directory checkpoint: a SHA-256 transcript bound to the authenticated relay node ID, the monotonic append-only account-map revision, and the sorted `username -> stable 64-byte long-term identity` map. The relay computes one checkpoint while holding the account map, serializes presence computation/fanout, and requires an exact-current checkpoint under the conversation transaction lock before admitting encrypted fanout. Text, attachment metadata, and read receipts carry the same node/revision/digest in both their authenticated encrypted payload and their outer frame; clients recompute the transcript and retain at most 32 checkpoints in RAM on web and Android.

Presence conflicts, cross-node stamps, newer or altered replay evidence, and inner/outer stamp mismatches fail closed before ACK or publication. A frame carrying an evicted unknown-old checkpoint is dropped without decryption or ACK. Logout and client restart clear checkpoint history; relay restart clears the relay's account and checkpoint state. This detects equivocation observed by communicating clients, but it is not a signed append-only transparency log: there is no signed append-only external witness or monitor, permanently partitioned or noncommunicating clients can evade gossip, RAM-only history resets lose the comparison anchor, and the 32-stamp cap can cause availability drops when an older valid frame is encountered.

Room credentials bind the account's stable identity to the MLS leaf, and the relay validates the exact current roster/epoch/digest before accepting transitions. This gives group epochs and efficient group rekey, but not an externally witnessed identity directory. A malicious relay can still equivocate toward partitioned or newly connected clients that lack a retained comparison anchor. Rooms also have no scalable participant safety-number ceremony, signed external transparency log, or multi-device device list.

### State rollback and recovery limits

Within a live client process, failed Olm/outer authentication is transactional and restores the pre-decryption ratchet checkpoint, so malformed or mismatched direct ciphertext cannot consume a one-time prekey or advance a session. MLS application/control processing likewise stages the native state and commits only after the relay accepts the exact encrypted snapshot revision; rejected operations restore the checkpoint, while ambiguous outcomes invalidate the local room state. Encrypted direct and MLS snapshots plus pending ciphertext exist only in relay RAM. This permits process-memory-only clients to recover after app-process death, but a malicious relay can withhold or replay an older encrypted snapshot. Because clients deliberately keep no persistent state, they have no independent monotonic counter or persistent rollback anchor with which to prove rollback after a fresh login. A relay restart destroys accounts, snapshots, pending messages, and replay windows together.

Direct delivery acknowledgements use an Ed25519 action signature bound to conversation, recipient, original sender, message ID, and consumed prekey. The relay emits `ack_result` only after the signed recipient-state update and pending removal; recipient publication waits for an exact accepted result for that same ID. MLS recipients use the equivalent exact `mls_snapshot_result` transaction before publishing staged application/control state. Failures fail closed. These are delivery/state durability signals, not cryptographic proof that a human read the message.

### Ephemeral attachment and wipe limits

Transactional publication prevents a staged upload from becoming downloadable unless the relay accepts the exact authenticated owner/chat/message transaction. A staged record is non-downloadable for all users, consumes the existing quotas, and expires after a 10-minute deadline clamped to final retention; the 30-second sweeper makes the worst-case pre-publication cleanup window about 10.5 minutes. Rejected, rolled-back, and never-sent messages do not publish staged bytes, while an accepted message still publishes if its result is lost. The client cleanup endpoint remains useful but cannot recall a record after publication, cannot recall in-flight bytes, and cannot recall bytes already handed to the operating-system or network kernel. A hostile recipient can still record or copy decrypted content. During a global wipe, the relay advances a purge epoch, drops queued data, and sends a priority `GLOBAL_WIPE` text frame followed by WebSocket close code `4001` with reason `purge`; clients treat that exact close as a purge even if the text frame is lost. Offline or uncooperative clients cannot receive a remote wipe. This reduces orphan exposure without adding disk state; attachment ciphertext, keys, and the cipher-v1 bulk blob remain unchanged, while direct metadata uses protocol v9 and room metadata uses protocol-v10 MLS.

### Direct safety-number interlock

Direct headers show a symmetric safety number derived from both identity keys. Android and web display `NOT COMPARED` until the user explicitly confirms an exact match obtained through a separate channel. Before that confirmation, direct text, GIF/media upload, attachment view/export/save, and network read receipts are blocked. Incoming unverified direct text may still display and update local read state, but the client emits no network read receipt. The same gate applies to both clients and to attachment operations reached from an incoming message.

The confirmation is a user assertion, not independent authentication, an external witness, or proof that the peer compared the value. Trust is RAM-only and bounded to 128 peers. Each record is keyed to the direct context, both stable long-term identity prefixes (the first 64 bytes), and the current session and connection generations. Rotating one-time prekeys are intentionally excluded, so prekey rotation preserves a comparison. Reconnect, identity change, logout, wipe, inactivity expiry, process/page teardown, or bounded-store eviction clears the affected trust. Rooms use protocol-v10 MLS; this direct-chat policy does not provide room participant verification or an external key-transparency witness.

### Active relay and web-delivery trust

An actively malicious relay can substitute recipient public keys before a sender has independently verified the direct safety number, and it can still present a conflicting or manipulated conversation context. Abyssal deliberately does not persist trust decisions because client account state is RAM-only, so verification must be repeated after process restart. For rooms there is no scalable key-transparency or participant-verification system yet.

The relay also serves the browser bundle. A compromised web origin can deliver modified JavaScript/WASM and capture plaintext before encryption. Signed native Android builds avoid this code-delivery dependency but still require release-key and device integrity.

### Browser RAM-only claims are limited

JavaScript cannot guarantee physical zeroization. Browser engines may copy immutable strings, page memory to swap, cache decoded media, retain back/forward state, or expose process data to privileged extensions and compromised devices. File pickers and Blob/media implementations may use temporary disk storage. OS screenshots, cameras, developer tools, and network inspection cannot be blocked reliably by a web page. The privacy-cover verifier keeps only salted PBKDF2-HMAC-SHA256 results in tab memory, wipes its mutable arrays on teardown, and serializes attempts with backoff; JavaScript timing and garbage collection still prevent a physical-zeroization or strict constant-time guarantee. `pagehide` synchronously revokes decrypted-media URLs, clears application refs/state, and hides the document before a back/forward-cache snapshot, but browser-internal copies remain outside application control.

To make this asymmetry visible per message, text and attachment plaintexts carry a sender-client origin tag asserted by the sending build. Android renders a small warning badge on every message sent from the web client (tappable for the full explanation) because that device may lack `FLAG_SECURE`-style screenshot protection and any memory-wipe guarantee; the web client marks messages sent from the hardened Android app informationally. A missing or unknown tag fails closed: the frame is never published and emits no read receipt, although the earlier relay-level acknowledgement has already consumed its pending entry, so it is not redelivered — the same semantics as any other rejected inner payload. This makes the change wire-incompatible with older clients that omit the field (Deployment Rule 6 applies). The tag is a claim inside the authenticated encrypted payload, not an attestation: it is as trustworthy as the rest of the decrypted plaintext, and a maliciously modified client build can mislabel itself.

Web client therefore provides no local forensic guarantee. Its security also depends on the web origin and the JavaScript/WASM bundle delivered by that origin. Use hardened native Android for threat models requiring screenshot controls and stronger OS integration. A one-time attachment view is a UI and relay-lifecycle control, not a defense against a recipient photographing, screen-recording, or otherwise copying decrypted content.

### Metadata remains visible

Relay and TLS endpoint observe IP addresses, timing, packet sizes, account sessions, usernames, room membership, presence, attachment sizes, and routing. Cloudflare terminates public TLS when used as the edge, so it can observe and modify application requests and responses at that boundary, including invite codes, OPAQUE protocol messages, routing metadata, encrypted payloads, and the delivered web bundle. OPAQUE still prevents the plaintext password from appearing in those requests, and E2EE keeps message/attachment plaintext out of the relay and edge, but Cloudflare is part of the availability, account-enrollment, and web-code-delivery trust boundary. Use a directly controlled TLS origin when that trust is unacceptable.

Canonical outer message-frame buckets reduce exact application-frame length leakage, but they do not provide anonymity or cover traffic. Required replacements depend on the threat model: sealed sender, batching, private contact discovery, optional cover traffic, and a reviewed proxy or anonymity layer.

## Deployment Rules

1. Serve production web and API from one HTTPS origin. Leave `ABYSSAL_WEB_ORIGINS` empty unless a separate reviewed origin is required.
2. Keep port `4020` private behind TLS tunnel or reverse proxy. Do not expose plaintext relay HTTP to internet.
3. Use the supplied Docker read-only runtime, no volumes, non-root UID, dropped capabilities, bounded memory/PIDs, and `no-new-privileges`.
4. Startup codes appear once in attached process stdout. The supplied Compose deployment disables Docker log persistence and provides no retrieval file, API, fixed-code environment setting, or plaintext-code map. Lost codes require a destructive restart. Do not replace this with a disk-backed log driver.
5. Restart wipes all relay state. Verify terminal capture, host tracing, crash dumps, and swap are not configured to capture process/container memory.
6. Rebuild Android and web clients after protocol changes. Current source keeps protocol-v9 OPAQUE/Olm direct chats and requires protocol-v10 MLS room clients with matching generated native/WASM bindings and strict schemas. Older protocol-v9 room clients have no pairwise fallback and fail closed; protocol-v8 clients/checkpoints and older pre-v8 clients are also wire-incompatible. No Android APK/AAB is produced by the normal security gate.
7. Keep the Android release keystore offline and backed up. Never commit `deploy/release.env`, `.secrets/`, APK signing credentials, or generated access codes.
8. Commission independent cryptographic and application security review before claiming Signal-grade, audited, or high-assurance security. Stable software releases must disclose the experimental RustCrypto MLS provider, absence of an external key-transparency witness, multi-device coordination, persistent rollback anchor, and independent audit, plus web origin/JavaScript limits, metadata exposure, one-time recording limits, bounded offline-generation availability loss, and the intentional global-wipe availability risk.

The repository pins security-sensitive toolchain versions, Gradle wrapper/distribution hashes, GitHub Action revisions, and Docker image/frontend digests. CI performs byte-for-byte crypto artifact regeneration, Rust/npm advisory checks, CodeQL analysis, and normal no-package Android compilation/tests. Gradle dependency verification metadata is required for Android dependency resolution. These controls reduce dependency and build drift; they do not make GitHub-hosted runners, package registries, maintainers, or release signing infrastructure intrinsically trustworthy.

Android update discovery requests only the configured official GitHub `releases/latest` API endpoint over HTTPS. The client disables redirects and caching for this request, accepts only stable semantic versions, and requires the APK asset name, repository path, HTTPS host, media type, and bounded size to match the expected release. Release metadata and reminder state remain in RAM. Pressing Update opens the official APK URL in the system browser; Android still requires normal user confirmation and a matching application signature before replacement.

A hostile host administrator can replace or instrument the relay binary, attach before startup output is zeroized, or capture incoming account requests. Software running on an administrator-controlled host cannot prevent that. This design removes recovery paths and plaintext retention after normal startup; it does not claim protection from a malicious root operator.

## Reporting

Private vulnerability reporting is enabled through GitHub Security Advisories. Use the repository's Security → Advisories → Report a vulnerability flow for security-sensitive findings; do not open a public issue first. Do not include access codes, passwords, bearer tokens, decrypted messages, or attachment contents. Share the minimal reproduction, affected commit/version, impact, and any safe remediation detail privately with repository maintainers.
