# Abyssal Security Model

No application has absolute security. Abyssal implements ratcheted end-to-end encryption and OPAQUE authentication, but it has not received an independent audit and must not be presented as Signal-equivalent.

## Current Protections

- Relay state is process memory only: keyed invite-code identifiers, OPAQUE password files, encrypted identity envelopes, sessions, room catalog, presence, recipient-specific pending ciphertext, and attachments have no database or volume. Plaintext invite codes exist only until their one-time startup print, then those buffers are zeroized.
- Android app-owned account, message, endpoint, PIN, password, token, and key state is process memory only. `FLAG_SECURE`, hidden-overlay rejection on Android 12+, and recents-screenshot disabling on Android 13+ reduce normal screen-capture and overlay exposure. Calculator camouflage keeps only salted PBKDF2-HMAC-SHA256 verifiers in RAM, compares derived values without early exit, serializes attempts, and applies bounded exponential backoff. Process death resets the launcher alias and verifier, there is no default PIN, and the user must configure camouflage again after a fresh process.
- Web client uses no persistent browser storage, cookies, service worker, source maps, or third-party runtime scripts. Identity keys live in the shared Rust/WASM core; typed password, plaintext, and key buffers are overwritten on a best-effort basis after use.
- OPAQUE registration and login use the shared Rust `opaque-ke` implementation. Password bytes never appear in relay application requests. Identity and ratchet snapshots are encrypted with an OPAQUE export-key-derived key before leaving the client.
- Protocol-v6 text, read-receipt, and control metadata use a fresh content key and ChaCha20-Poly1305 with conversation/message/sender additional data. Each recipient's content key is wrapped through an authenticated `vodozemac` Olm Double Ratchet session configured for a full-length HMAC. Every recipient envelope contains exactly one 64-byte Ed25519 signature over the v6 version, authenticated context, common nonce/ciphertext, sender identity key, intended username, prekey metadata, and recipient-specific ratchet envelope. Before claiming prekeys, registering replay IDs, or applying an identity revision, the relay verifies that signature with the authenticated account's long-term Ed25519 identity and the shared Rust-core transcript builder. Initial asynchronous messages use a recipient-specific one-time prekey, which is rotated after successful decryption. Prekey IDs are deterministic commitments to their public keys; recipients verify relay metadata against the one-time key inside the Olm envelope before changing ratchet state. The relay claims an advertised prekey for an idle 10-minute claim window; if its matching ciphertext is still queued, the claim remains until acknowledgement, eviction, queue removal, or the bounded pending-message TTL. This queued-lifetime rule prevents concurrent deliveries from claiming the same prekey, including when a frame waits longer than 10 minutes, while the default 24-hour pending TTL prevents an offline queue from holding a prekey indefinitely. The TTL is configurable through `ABYSSAL_PENDING_MESSAGE_TTL_HOURS` and clamped to 1-168 hours; zero is never treated as unbounded. The relay receives ciphertext, signatures, public identity bundles, prekey metadata, ratchet envelopes, and OPAQUE-encrypted state snapshots, not plaintext or ratchet secrets.
- Decryption is transactional around ratchet state. If Olm processing advances a session but outer AEAD/content-binding authentication, prekey rotation, revision update, or state sealing fails, the client restores the account, peer sessions, session-prekey map, advertised prekey metadata, and revision from a vodozemac pickle checkpoint before returning an error. A failed initial delivery therefore does not consume or rotate the one-time prekey.
- Successful encryption and decryption advance a monotonic ratchet-state revision. The relay keeps only the latest encrypted snapshot in RAM, uses a 128-revision replay window to accept bounded network reordering without accepting a message revision twice, and never replaces newer state with an older snapshot. Recipient ciphertext remains queued until a sender-bound acknowledgement follows successful decryption.
- The relay authoritatively binds delivered sender usernames/public keys to authenticated accounts and rejects missing, duplicate, or unauthorized recipient envelope sets. Clients reject malformed, tampered, wrongly addressed, or misbound payloads before parsing plaintext.
- Direct conversations display a symmetric safety number derived from both identity public keys. Comparing it through a separate channel detects active relay key substitution for that conversation.
- TLS/WSS is required for remote web nodes loaded from HTTPS. Loopback HTTP remains available for development.
- WebSocket bearer tokens are sent as a WebSocket subprotocol value, not in request URLs. Browser WebSocket origins must match the node host or an exact `ABYSSAL_WEB_ORIGINS` entry.
- Relay responses set a restrictive CSP, no-store caching, frame denial, no-referrer, MIME sniffing denial, HSTS, permissions restrictions, and cross-origin headers.
- Browser account responses are read through a strict 768 KiB streaming cap with fatal UTF-8 decoding and bounded canonical fields. Browser and Android relay text frames are capped at 1 MiB before JSON parsing; an oversized frame fails the authenticated socket closed. Web `pagehide` synchronously revokes decrypted Blob URLs, clears session/message/navigation references and React state, destroys PIN verifiers, and hides the document before a possible back/forward-cache snapshot.
- Login and registration request bodies are capped at 16 KiB, OPAQUE handshakes expire after 60 seconds and are capped at 1,024 live entries, and known account-code starts are limited to six per minute. Unknown HMAC-derived code IDs are rejected before they can allocate limiter state, so random-code floods cannot fill the bounded map and deny real invite holders. WebSocket frame size/rate, outbound frame size, pending queue depth (500 frames per recipient and 256 MiB globally), pending-message lifetime (default 24 hours, clamped to 1-168 hours), session inactivity, and per-user room count are bounded.
- Attachment plaintext limits are 20 MiB for images, 100 MiB for videos, and 200 MiB for other files. Bulk data uses a stateless binary XChaCha20-Poly1305 blob: one version byte, a 24-byte nonce, ciphertext, and a 16-byte tag, for exactly 41 bytes of wire overhead. The attachment key is delivered inside encrypted ratcheted message metadata; the relay never receives it. Encrypted attachment RAM is bounded globally and per account (default per-account quota: 320 MiB). Every blob also has a finite relay-side expiry: `ABYSSAL_ATTACHMENT_MAX_LIFETIME_HOURS` defaults to 168 hours and is clamped to 1-720 hours, so an explicit `ttl=0` cannot leave an orphan immortal in RAM. Room absolute-expiry policy can shorten this hard cap. Upload request-body reads are capped at two concurrent bodies by default (maximum four), with a 30-second idle and 10-minute total deadline. Downloads use a separate bounded concurrency semaphore (default: 2; maximum: 16) and a capacity-one producer that releases its zeroizing buffer and permit after 30 seconds of backpressure, so large or stalled transfers cannot retain unbounded extraction resources.
- Destructive attachment retention is explicit and recipient-scoped. A DM snapshots its intended peer and a room snapshots eligible members other than the uploader at upload time. The owner can preview without consuming a claim; each eligible recipient can have one active claim, and transport EOF alone never consumes it. The client must receive the exact positive `Content-Length`, authenticate and decrypt the ciphertext, then explicitly complete the recipient-bound claim before exposing plaintext. Failed, truncated, interrupted, cancelled, or unauthenticated transfers release the claim for retry; concurrent claims by the same recipient are rejected; and the relay removes the encrypted blob and releases its quota only after every eligible recipient completes or the retention policy expires it. A one-time UI cannot prevent a malicious recipient from recording or copying content after decryption.
- Account-entry attempts are rate-limited per code, and a code cannot create a concurrent bearer session while its existing session remains unexpired.
- Relay and clients maintain bounded RAM replay windows keyed by conversation, authenticated sender, and message ID. Ratchet message keys are consumed after use, so cryptographic replays also fail. Duplicate ciphertext and receipt frames are rejected without growing unbounded state; each authenticated sender has a bounded live-entry quota, and saturated sender/global windows reject new IDs rather than evicting live entries and weakening the replay guarantee.
- Clients pin each observed account identity key for the current RAM session and terminate/drop state if that key changes. First-contact authenticity still requires out-of-band safety-number comparison.
- Sender usernames on delivered frames come from the authenticated relay session, not user-controlled encrypted metadata.
- Client and relay identity ingress reject malformed, zero, non-contributory, and known low-order X25519 public keys. One-time prekey identifiers are verified as commitments to the exact advertised public key before ratchet state changes.
- Room ownership and media-retention policy are enforced by the relay. Canonical DMs are visible only to their participants, and guessed chat IDs cannot be used to join a DM or transfer its attachments.
- Any authenticated account can request the global RAM wipe by product design. This is an intentional availability tradeoff: compromise of one live account can destroy every account, room, pending frame, attachment, and invite-code set, forcing a visible destructive restart. The client keeps a confirmation step, but this is not an authorization boundary.
- Android and web attachment saves are explicit user actions. Clients authenticate and decrypt attachment ciphertext in memory, write the original bytes under a sanitized original filename, and best-effort wipe temporary byte arrays. One-time attachments have no save control. Saved files are plaintext by explicit user choice and inherit the destination provider's security. Android `2.0.0` and later also delete the obsolete device-bound export key created by older releases.

## Known High-Risk Gaps

### Initial prekey and group-key limits

Protocol v6 uses pairwise Olm Double Ratchet sessions. Deleted message keys provide the ratchet's forward-secrecy property, and reciprocal DH-ratchet steps provide recovery within an established session after key turnover. Per-recipient Ed25519 signatures authenticate the v6 envelope binding, while attachment keys are delivered as ratcheted metadata and bulk bytes use a separate stateless XChaCha20-Poly1305 blob. Initial asynchronous sessions consume a recipient-specific one-time prekey and rotate it after use. The relay enforces one live WebSocket session per account. A prekey claim expires after 10 minutes only when no matching pending frame remains; a queued frame keeps its claim until acknowledgement, eviction, queue removal, or the bounded pending-message TTL. The default pending TTL is 24 hours and accepts only 1-168 hours, so a delayed ciphertext cannot race a later sender for the same one-time prekey or hold it indefinitely. This is still an availability tradeoff while the frame remains queued. The design is still not MLS: rooms use pairwise fanout, prekey replenishment is one-at-a-time rather than a signed batch service, and multi-device session coordination is not implemented.

### Directory verification limits

Presence includes a deterministic directory checkpoint over usernames and stable long-term identity keys. Clients reject inconsistent checkpoints in one presence update and pin each peer's long-term identity across one-time-prekey rotation. This is a useful out-of-band comparison signal, not a signed append-only transparency log: the relay can still equivocate between clients, and there is no independent witness or monitor service yet.

Rooms encrypt the same content separately to every account through pairwise sessions. There is no MLS group epoch, membership transcript, efficient group rekey, or multi-device device list. Large rooms therefore have linear envelope cost and weaker membership-change semantics than a reviewed MLS design.

### State rollback and recovery limits

Within a live client process, failed Olm/outer authentication is transactional and restores the pre-decryption ratchet checkpoint, so malformed or mismatched ciphertext cannot consume a one-time prekey or advance a session. Encrypted ratchet snapshots and pending ciphertext exist only in relay RAM. This permits process-memory-only clients to recover a session after app-process death, but a malicious relay can withhold or replay an older encrypted snapshot. Because clients deliberately keep no persistent state, they have no independent monotonic counter or persistent rollback anchor with which to prove rollback after a fresh login. A relay restart destroys accounts, snapshots, pending messages, and replay windows together.

Delivery acknowledgements are authenticated by the WebSocket session and bound to conversation, recipient, original sender, and message ID. They are transport durability signals, not cryptographic proof to the sender that a human read the message.

### Active relay and web-delivery trust

An actively malicious relay can substitute recipient public keys before a sender has independently verified the direct safety number. Abyssal deliberately does not persist trust decisions because client account state is RAM-only, so verification must be repeated after process restart. For rooms there is no scalable key-transparency or participant-verification system yet.

The relay also serves the browser bundle. A compromised web origin can deliver modified JavaScript/WASM and capture plaintext before encryption. Signed native Android builds avoid this code-delivery dependency but still require release-key and device integrity.

### Browser RAM-only claims are limited

JavaScript cannot guarantee physical zeroization. Browser engines may copy immutable strings, page memory to swap, cache decoded media, retain back/forward state, or expose process data to privileged extensions and compromised devices. File pickers and Blob/media implementations may use temporary disk storage. OS screenshots, cameras, developer tools, and network inspection cannot be blocked reliably by a web page. The privacy-cover verifier keeps only salted PBKDF2-HMAC-SHA256 results in tab memory, wipes its mutable arrays on teardown, and serializes attempts with backoff; JavaScript timing and garbage collection still prevent a physical-zeroization or strict constant-time guarantee. `pagehide` synchronously revokes decrypted-media URLs, clears application refs/state, and hides the document before a back/forward-cache snapshot, but browser-internal copies remain outside application control.

Web client therefore provides no local forensic guarantee. Its security also depends on the web origin and the JavaScript/WASM bundle delivered by that origin. Use hardened native Android for threat models requiring screenshot controls and stronger OS integration. A one-time attachment view is a UI and relay-lifecycle control, not a defense against a recipient photographing, screen-recording, or otherwise copying decrypted content.

### Metadata remains visible

Relay and TLS endpoint observe IP addresses, timing, packet sizes, account sessions, usernames, room membership, presence, attachment sizes, and routing. Cloudflare terminates public TLS when used as the edge, so it can observe and modify application requests and responses at that boundary, including invite codes, OPAQUE protocol messages, routing metadata, encrypted payloads, and the delivered web bundle. OPAQUE still prevents the plaintext password from appearing in those requests, and E2EE keeps message/attachment plaintext out of the relay and edge, but Cloudflare is part of the availability, account-enrollment, and web-code-delivery trust boundary. Use a directly controlled TLS origin when that trust is unacceptable.

Required replacement depends on threat model: sealed sender, message padding, batching, private contact discovery, optional cover traffic, and a reviewed proxy or anonymity layer.

## Deployment Rules

1. Serve production web and API from one HTTPS origin. Leave `ABYSSAL_WEB_ORIGINS` empty unless a separate reviewed origin is required.
2. Keep port `4020` private behind TLS tunnel or reverse proxy. Do not expose plaintext relay HTTP to internet.
3. Use the supplied Docker read-only runtime, no volumes, non-root UID, dropped capabilities, bounded memory/PIDs, and `no-new-privileges`.
4. Startup codes appear once in attached process stdout. The supplied Compose deployment disables Docker log persistence and provides no retrieval file, API, fixed-code environment setting, or plaintext-code map. Lost codes require a destructive restart. Do not replace this with a disk-backed log driver.
5. Restart wipes all relay state. Verify terminal capture, host tracing, crash dumps, and swap are not configured to capture process/container memory.
6. Rebuild Android and web clients after protocol changes; protocol-v6 OPAQUE/ratcheted E2EE with per-recipient signatures and one-time prekeys requires Android version `2.0.0`/versionCode `16` and matching web clients. Protocol-v5/1.9.x clients are wire-incompatible.
7. Keep the Android release keystore offline and backed up. Never commit `deploy/release.env`, `.secrets/`, APK signing credentials, or generated access codes.
8. Commission independent cryptographic and application security review before claiming Signal-grade, audited, or high-assurance security. Stable software releases must continue disclosing the absence of MLS, a key-transparency witness, multi-device coordination, a persistent rollback anchor, and an independent audit, along with web origin/JavaScript limitations, metadata exposure, one-time recording limits, and the global-wipe availability risk.

The repository pins security-sensitive toolchain versions, Gradle wrapper/distribution hashes, GitHub Action revisions, and Docker image/frontend digests. CI performs byte-for-byte crypto artifact regeneration, Rust/npm advisory checks, CodeQL analysis, and normal no-package Android compilation/tests. Gradle dependency verification metadata is required for Android dependency resolution. These controls reduce dependency and build drift; they do not make GitHub-hosted runners, package registries, maintainers, or release signing infrastructure intrinsically trustworthy.

Android update discovery requests only the configured official GitHub `releases/latest` API endpoint over HTTPS. The client disables redirects and caching for this request, accepts only stable semantic versions, and requires the APK asset name, repository path, HTTPS host, media type, and bounded size to match the expected release. Release metadata and reminder state remain in RAM. Pressing Update opens the official APK URL in the system browser; Android still requires normal user confirmation and a matching application signature before replacement.

A hostile host administrator can replace or instrument the relay binary, attach before startup output is zeroized, or capture incoming account requests. Software running on an administrator-controlled host cannot prevent that. This design removes recovery paths and plaintext retention after normal startup; it does not claim protection from a malicious root operator.

## Reporting

Do not include access codes, passwords, bearer tokens, decrypted messages, or attachment contents in an issue. Share minimal reproduction details privately with repository maintainers.
